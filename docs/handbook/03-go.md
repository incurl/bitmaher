# Chapter 3 — Go

Go is the language of the backend, and it is the language of the parts that have to be right:
starting a process, owning a lifetime, sharing state without a data race, and crossing a boundary
into a library that was not written for this.

This chapter is about the parts of Go that this application leans on, and the corners of them that
catch people out.

The version is **1.26**, pinned in `go.mod`:

```
go 1.26.0
toolchain go1.26.10
```

## The shape of the backend

There is no framework here. There is a `main.go` that wires things together and a set of packages
under `internal/` that do one job each:

```
internal/aria2/       the sidecar: its lifecycle, its RPC client, its types
internal/bindings/    the API surface: the methods the frontend may call
internal/console/     the in-memory debug log
internal/downloads/   the domain: the records, the status mapping, the service
internal/pocketbase/  the persistence: the service, the settings, the crypto, the migrations
internal/pump/        the reader: the single ticker of the engine's state
```

The rule that keeps this readable: **each package owns one thing, and the packages depend on each
other in one direction.**

```
bindings → downloads → aria2 → console
   ↓           ↓
pocketbase   (the database)
```

`internal/aria2` knows nothing about the domain. `internal/downloads` knows nothing about Wails.
`internal/bindings` is the only package that knows about both, and it is the only one the frontend
can reach.

## Nook 1: a `context.Context` is a deadline, not a cancellation of the caller

The context is how a call is bounded in time. The rule is that the **caller** sets the deadline and
the **callee** honours it.

Here is the pump's read of the engine:

```go
// internal/pump/pump.go
func (p *Pump) tick() {
    if p.source == nil || p.emitter == nil {
        return
    }
    ctx, cancel := context.WithTimeout(context.Background(), ReadTimeout)
    defer cancel()

    snapshot, err := p.source.Snapshot(ctx)
    if err != nil {
        // The engine may be restarting. The next tick will try again,
        // and the frontend keeps the last snapshot it had.
        return
    }
    p.emitter.EmitSnapshot(snapshot)
}
```

The context is **not** derived from anything the pump holds. It is `context.Background()` with a
timeout, because the pump's lifetime is the application's lifetime, and the timeout is what stops a
wedged engine from blocking the tick forever.

The same shape appears in the RPC client, where the context travels into the HTTP request:

```go
// internal/aria2/rpcclient.go
req, err := http.NewRequestWithContext(ctx, http.MethodPost, c.endpoint, bytes.NewReader(payload))
```

and where the client itself carries a timeout, as a belt to the braces:

```go
http: &http.Client{
    Timeout: DefaultTimeout,   // 10 seconds
},
```

**The timeout is there so that a wedged sidecar cannot hang a UI call forever.** A desktop
application that freezes because a child process stopped answering is a bad application.

## Nook 2: a mutex is not a queue

The `Manager` has a lot of state that several goroutines touch: the sidecar's process, its port,
its client, its readiness. It is guarded by one mutex:

```go
type Manager struct {
    mu sync.Mutex
    // ...
}
```

The discipline that matters: **take the lock, read what you need, copy it out, release the lock.**
Do not call anything that might block while you hold it.

```go
// internal/aria2/manager.go — the pattern, done right
func (m *Manager) Endpoint() string {
    m.mu.Lock()
    defer m.mu.Unlock()
    if m.port == 0 {
        return ""
    }
    return fmt.Sprintf("http://127.0.0.1:%d/jsonrpc", m.port)
}
```

And the pattern done wrong, which the code avoids:

```go
// NOT what the code does: the lock is held across a network call.
m.mu.Lock()
defer m.mu.Unlock()
response, err := m.client.Version(ctx)   // blocks for milliseconds, holding the lock
```

The watchdog shows the shape you want when the work is long. It reads the state it needs under the
lock, then releases it before doing anything slow:

```go
m.mu.Lock()
waitDone := m.waitDone
enabled := m.autoRestart
m.mu.Unlock()

select {
case <-ctx.Done():
    return
case <-waitDone:
case <-time.After(watchdogInterval):
    continue
}
```

### The atomic flag

Not everything needs a mutex. A flag that is set and read from different goroutines wants an atomic:

```go
// internal/bindings/window.go
type WindowCloser struct {
    // held says whether the close is still being held.
    //
    // The flag is atomic, because the hook and the release run on
    // different goroutines: the hook runs on the thread of the window
    // manager, and the release comes from the frontend's request.
    held atomic.Bool
    // ...
}
```

`atomic.Bool` rather than a plain `bool` under the mutex, because the check in the hook must be as
cheap as possible — it runs on the window's thread, inside the event loop.

## Nook 3: exactly one goroutine may wait for a process

This is a rule of `os/exec` that is easy to break and produces a baffling symptom: a zombie.

`cmd.Wait()` may be called **once**. Two goroutines calling it will fight over the exit status, and
one of them gets an error that means nothing.

The manager therefore has exactly one waiter:

```go
type Manager struct {
    // cmd is the running sidecar, if there is one.
    cmd *exec.Cmd
    // waitDone is closed when the sidecar process has exited.
    //
    // Exactly one goroutine waits for the process, so that the exit
    // status is never read twice.
    waitDone chan struct{}
    // exitCode is the code the sidecar exited with, once it has.
    exitCode int
    // ...
}
```

And the channel is how the rest of the program learns about it. `waitDone` is closed when the
process is gone, and the watchdog selects on it:

```go
select {
case <-ctx.Done():
    return
case <-waitDone:
    // The sidecar has left. The watchdog decides whether
    // that was a crash or a deliberate stop.
case <-time.After(watchdogInterval):
    continue
}
```

The same rule appears in the relaunch code, for the same reason:

```go
// The child is not waited for: it outlives this process on
// purpose. Releasing it here keeps a zombie out of the table.
go func() { _ = cmd.Wait() }()
```

## Nook 4: `close()` a channel once, and never send to a closed one

The pump's `Wake` is the textbook example:

```go
func (p *Pump) Wake() {
    if p == nil {
        return
    }

    p.mu.Lock()
    wake := p.wake
    p.mu.Unlock()

    select {
    case wake <- struct{}{}:
    default:
        // A tick is already pending. The one that is on its way will
        // pick the change up, so there is nothing to do.
    }
}
```

Two things are happening:

1. **The `default` branch makes the send non-blocking.** The pump must never be blocked by a
   caller that wants to hurry it along. If a tick is already queued, the one on its way will see the
   change anyway.
2. **The channel is read under the lock and used outside it.** Reading `p.wake` under the lock and
   then sending without it would be a race with a future replacement of the channel.

The counterpart — how a channel is closed exactly once — is in `Stop`:

```go
func (p *Pump) Stop() {
    // ...
    stop := p.running
    done := p.stopped
    p.running = nil
    p.stopped = nil
    p.mu.Unlock()

    if stop == nil {
        return          // already stopped: harmless
    }

    close(stop)
    <-done            // and wait for the last tick to finish
}
```

Taking the channels out from under the lock, then closing them outside it, means `Stop` is safe to
call twice and safe to call on a pump that was never started. The `<-done` is what makes the
shutdown **ordered**: the last tick finishes before the sidecar is stopped, so the pump is never
reading an engine that is on its way out.

That ordering is why `main.go` stops the pump *before* the sidecar:

```go
OnShutdown: func() {
    // The pump stops before the sidecar, so that it
    // does not read an engine that is on its way out.
    enginePump.Stop()
    // ...
    if err := sidecar.Stop(shutdownCtx); err != nil { ... }
},
```

## Nook 5: `sync.Once` and the "started already" check

The pump's `Start` has the guard you see in almost every Go object with a lifecycle:

```go
func (p *Pump) Start() {
    if p == nil {
        return
    }

    p.mu.Lock()
    defer p.mu.Unlock()

    if p.running != nil {
        return          // already running
    }
    // ...
}
```

Note the `if p == nil` at the top. Go's method receivers can be nil, and a method on a nil pointer
does not crash by itself — it panics the moment it dereferences the pointer. The nil check turns
"the caller forgot to set it" into a no-op instead of a crash.

This is why `SetQuitter` and the other setters all begin with a nil check:

```go
func SetQuitter(service *AppService, quit func()) {
    if service == nil {
        return
    }
    service.quit = quit
}
```

## Nook 6: a free port is a race you have to accept

Finding a free port is done by binding it and letting the operating system choose:

```go
// internal/aria2/manager.go
func freePort() (int, error) {
    listener, err := net.Listen("tcp", "127.0.0.1:0")
    if err != nil {
        return 0, fmt.Errorf("aria2: find a free port: %w", err)
    }
    defer listener.Close()

    addr, ok := listener.Addr().(*net.TCPAddr)
    if !ok {
        return 0, fmt.Errorf("aria2: the listener has an unexpected address")
    }
    return addr.Port, nil
}
```

Between the `Close()` and the sidecar binding the port, another process can take it. The code says
so in a comment and then **handles it**:

```go
const portAttempts = 5
for attempt := 0; attempt < portAttempts; attempt++ {
    port, err := freePort()
    // ...
    if err := m.launch(binary, port, secret); err != nil {
        lastErr = err
        // A port that is taken is the one failure worth
        // retrying: the next port is likely free.
        if strings.Contains(err.Error(), "Address already in use") {
            continue
        }
        return "", err
    }
    // ...
}
```

Matching on the error string is not elegant, and it is the right trade here: the alternative is a
hand-rolled handshake, and the failure being retried is genuinely rare.

## Nook 7: a child process must be put in its own process group

When the application starts the sidecar, it must not be in the same process group as the
application — otherwise a signal aimed at the group takes the child with it, or leaves it behind.

```go
// internal/aria2/process_unix.go (and process_windows.go for the other platform)
cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}
```

The same file has the counterpart for the restart, which needs to **outlive** its parent:

```go
// internal/bindings/process_unix.go
func detachedProcessAttributes() *syscall.SysProcAttr {
    return &syscall.SysProcAttr{Setpgid: true, Setsid: true}
}
```

`Setsid` starts a new session, so the restarted application survives the terminal it was started
from. The two are different tools for different jobs, and the comments say which is which.

**This is also why the platform-specific files exist at all.** `syscall.SysProcAttr` has different
fields on different operating systems, and the build tags keep the two apart:

```go
//go:build !windows
```

## Nook 8: `os.Executable` and the path of the running program

The restart has to start *this* program again, with *its* arguments:

```go
// internal/bindings/relaunch.go
executable, err := os.Executable()
if err != nil {
    return err
}
if resolved, err := filepath.EvalSymlinks(executable); err == nil {
    executable = resolved
}

cmd := exec.Command(executable, os.Args[1:]...)
```

The `EvalSymlinks` is there because the path may be a symlink — a launcher, a package manager's
shim — and the resolved path is the real program.

## Nook 9: the restart has to wait for the old instance

A restart starts the new instance **as the old one goes down**. The old instance still holds the
SQLite database, and the two would fight over it.

So the new instance is told who started it, and waits:

```go
cmd.Env = append(os.Environ(),
    EnvRelaunchParent+"="+strconv.Itoa(os.Getpid()),
)
```

and at the very start of the new process, **before anything touches the database**:

```go
// main.go
func run() error {
    // --- The restart ------------------------------------------------
    // A restart starts the new instance as the old one goes down. The
    // old one still holds the database when it does, so the new one
    // waits here, before it touches anything: the database belongs to
    // one process at a time.
    bindings.WaitForPreviousInstance()

    // --- PocketBase ------------------------------------------------
    pbService := pocketbase.NewService(dataDir())
```

The wait is bounded, so a process that does not go away cannot hold the new one hostage:

```go
const previousInstanceTimeout = 15 * time.Second
```

And the check for "is that process still there" is platform-specific, because the answer is:

```go
// process_unix.go — signal 0 asks without sending anything
func processExists(pid int) bool {
    process, err := os.FindProcess(pid)
    if err != nil {
        return false
    }
    return process.Signal(syscall.Signal(0)) == nil
}

// process_windows.go — Windows has no signal 0, so the handle is asked
func processExists(pid int) bool {
    // ...
    var code uint32
    if err := syscall.GetExitCodeProcess(handle, &code); err != nil {
        return false
    }
    // The exit code of a process that is running is still the constant
    // one the system gives.
    const stillActive = 259
    return code == stillActive
}
```

## Nook 10: the `defer` that must not be in a loop

A `defer` runs when the **function** returns, not when the block ends. In a loop, that means every
defer piles up until the function returns.

The classic bug:

```go
// NOT what the code does.
for _, path := range paths {
    f, err := os.Open(path)
    if err != nil { return err }
    defer f.Close()   // all of them pile up
}
```

The code in this repository avoids it by extracting the body into a function:

```go
for _, name := range names {
    if err := processOne(name); err != nil {
        return err
    }
}
```

## Nook 11: errors are wrapped with `%w`, and the message says what failed

The convention in this codebase: `fmt.Errorf("verb the thing: %w", err)`.

```go
return fmt.Errorf("bootstrap pocketbase: %w", err)
return fmt.Errorf("initialise settings encryption: %w", err)
return fmt.Errorf("create data dir: %w", err)
```

The verb comes first, so the message reads as a sentence about what the program was doing:
*"bootstrap pocketbase: ..."*.

`%w` rather than `%v` because it **wraps**: the caller can use `errors.Is` and `errors.As` to look
inside.

```go
if errors.Is(err, os.ErrNotExist) { ... }
```

The one place that inspects an error's *text* is the port retry, and it says why:

```go
// A port that is taken is the one failure worth
// retrying: the next port is likely free.
if strings.Contains(err.Error(), "Address already in use") {
    continue
}
```

## Nook 12: `errors.As` and the typed error

Sometimes you want to know the *kind* of an error, not its text. `errors.As` walks the chain:

```go
var target *MyError
if errors.As(err, &target) {
    // handle it
}
```

The `aria2` package defines its own sentinel:

```go
// ErrNotRunning is returned when the sidecar is asked to do something
// while it is not running.
var ErrNotRunning = errors.New("aria2: the sidecar is not running")
```

and the callers compare with `errors.Is`.

## Nook 13: the race detector is not optional

```bash
go test -race ./internal/... .
```

This repository runs it on every change, and it earns its keep: the whole application is a set of
goroutines talking to a child process, and the mistakes that matter are the ones that only show up
under load, on a different machine, weeks later.

The race detector finds them at test time, on your machine, today.

## Nook 14: `go vet` catches the mistakes the compiler does not

```bash
go vet ./internal/... .
```

`vet` is not a style checker. It finds real bugs: a `Printf` whose arguments do not match the
format string, a lock copied by value, an unreachable branch.

## Nook 15: the `//go:build` tags

Two kinds of build tag are in play.

**The platform ones**, which keep the operating-system differences apart:

```go
//go:build !windows
```

**The `server` and `production` ones**, which select the build:

```bash
go build -tags server,production -o "bin/bitmaher-server"
```

And there is one tag that surprises everybody:

```go
//go:build ios
```

`build/ios` is a separate `main` package behind that tag, so `go build ./...` fails with
*"function main is undeclared in the main package"*. That is the known rough edge: build the root
package and `./internal/...` instead.

## Nook 16: the `//go:embed` payload

```go
//go:embed all:frontend/dist
var assets embed.FS
```

`all:` is there for a reason: without it, `go:embed` skips files and directories whose names begin
with `_` or `.`. The `all:` prefix includes them.

The payload is built by Vite and is **gitignored**. It is never hand-edited.

## Nook 17: the `internal` directory is a rule, not a convention

`internal/` is enforced by the compiler: a package under `internal/` cannot be imported from
outside the tree. The rule is a boundary the tool enforces, which is worth more than a boundary
that is only written down.
